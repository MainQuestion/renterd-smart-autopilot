# renterd v0.3.2-rc.1 — Release Notes

## Исправление Smart Autopilot: защита от избыточной замены контрактов при Gouging

### Проблема

В логике управления контрактами была обнаружена важная проблема: обнаружение Gouging у действующего хоста могло приводить к созданию нового контракта независимо от того, сохранялась ли достаточная избыточность портфеля.

Для распределённого хранения это создавало риск ненужного роста количества контрактов и расходов. При Reed-Solomon **3/5** потеря одного или нескольких хостов по экономической причине не должна автоматически заставлять renterd немедленно создавать новые контракты, пока портфель сохраняет достаточный запас Good-контрактов.

`WantedContracts` при этом является целевым размером портфеля, а не критерием безопасности Reed-Solomon. Эти два понятия должны рассматриваться независимо.

### Что исправлено

В Smart Autopilot добавлен отдельный **Gouging Redundancy Guard**, который учитывает фактическое количество `Good`-контрактов и параметры Reed-Solomon.

Для протестированной конфигурации:

- `MinShards (K) = 3`
- `TotalShards (N) = 5`
- Safety Margin = 2
- `WantedContracts = 10` остаётся независимым параметром размера портфеля.

Правила:

- `Good >= N + 2` — замена из-за Gouging не требуется;
- `N <= Good < N + 2` — замена не выполняется немедленно, контракту даётся время `MaxDowntimeHours`;
- `Good < N` — замена разрешается немедленно, поскольку портфель опустился ниже количества shards, необходимого для восстановления.

Дополнительно:

- `Good` определяется по фактической usability контракта;
- `Paused` и `Bad` не считаются Good;
- `Replaced + Good` продолжает занимать слот портфеля;
- `WantedContracts` не используется как критерий RS-безопасности.

### Почему это важно

Исправление предотвращает каскадную реакцию:

> один Gouging-хост → новый контракт → ещё один Gouging-хост → ещё один новый контракт → ненужный рост портфеля.

Теперь Smart Autopilot оценивает Gouging в контексте всего портфеля и его способности восстановить данные.

### Проверка

Во время тестирования RS **3/5**:

- 2 Gouging-контракта не вызвали создание новых контрактов;
- 3 Gouging-контракта не вызвали создание новых контрактов;
- когда условие замены стало выполняться, Smart выполнил точечную замену одного Gouging-контракта;
- после замены исходный контракт перешёл в lifecycle `Legacy`, а новый контракт был успешно создан.

Также подтверждено, что временный `Offline` является отдельным operational-состоянием и не используется как автоматическая причина Gouging replacement.

### Результат

Smart Autopilot больше не трактует каждый Gouging-контракт как безусловную команду немедленно создать новый контракт. Решение теперь учитывает **K/N Reed-Solomon, запас Good-контрактов и фактическую безопасность портфеля**.

Исправление закрывает обнаруженную дыру в политике Gouging replacement, сохраняя пользовательский параметр `WantedContracts` и существующие низкоуровневые механизмы renterd.
