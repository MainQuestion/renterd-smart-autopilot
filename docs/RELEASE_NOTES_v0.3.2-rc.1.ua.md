# renterd v0.3.2-rc.1 — Release Notes

## Виправлення Smart Autopilot: запобігання надлишковій заміні контрактів через Gouging

### Проблема

У логіці керування контрактами було виявлено важливу прогалину: виявлення Gouging у діючого хоста могло призводити до створення нового контракту незалежно від того, чи зберігав портфель достатню надлишковість.

Для розподіленого зберігання це могло спричиняти непотрібне збільшення кількості контрактів і витрат. При Reed-Solomon **3/5** втрата одного або кількох хостів через економічну неприйнятність не повинна автоматично змушувати renterd негайно створювати нові контракти, доки портфель має достатній запас Good-контрактів.

`WantedContracts` є цільовим розміром портфеля, а не критерієм безпеки Reed-Solomon. Ці два поняття мають залишатися незалежними.

### Що виправлено

До Smart Autopilot додано окремий **Gouging Redundancy Guard**, який враховує фактичну кількість `Good`-контрактів та параметри Reed-Solomon.

Для протестованої конфігурації:

- `MinShards (K) = 3`
- `TotalShards (N) = 5`
- Safety Margin = 2
- `WantedContracts = 10` залишається незалежним параметром розміру портфеля.

Правила:

- `Good >= N + 2` — заміна через Gouging не потрібна;
- `N <= Good < N + 2` — заміна не виконується негайно, контракту надається час `MaxDowntimeHours`;
- `Good < N` — заміна дозволяється негайно, оскільки портфель опустився нижче кількості shards, необхідної для відновлення.

Додатково:

- `Good` визначається за фактичною usability контракту;
- `Paused` і `Bad` не враховуються як Good;
- `Replaced + Good` продовжує займати слот портфеля;
- `WantedContracts` не використовується як критерій RS-безпеки.

### Чому це важливо

Виправлення запобігає каскадній реакції:

> один Gouging-хост → новий контракт → ще один Gouging-хост → ще один новий контракт → непотрібне зростання портфеля.

Тепер Smart Autopilot оцінює Gouging у контексті всього портфеля та його здатності відновити дані.

### Перевірка

Під час тестування з RS **3/5**:

- 2 Gouging-контракти не спричинили створення нових контрактів;
- 3 Gouging-контракти не спричинили створення нових контрактів;
- коли умова заміни стала виконуватися, Smart здійснив точкову заміну лише одного Gouging-контракту;
- після заміни старий контракт перейшов у lifecycle `Legacy`, а новий контракт був успішно створений.

Також підтверджено, що тимчасовий `Offline` є окремим операційним станом і не використовується як автоматична причина Gouging replacement.

### Результат

Smart Autopilot більше не трактує кожен Gouging-контракт як безумовну команду негайно створити новий контракт. Рішення тепер враховує **K/N Reed-Solomon, запас Good-контрактів та фактичну безпеку портфеля**.

Це закриває виявлену прогалину в політиці Gouging replacement, зберігаючи налаштовуваний користувачем параметр `WantedContracts` та існуючі низькорівневі механізми renterd.
