## Что изменилось

### Smart Autopilot

**Economics (`5fda9927`, `8a45444d`, `ab3163e7`).**
- Залог корректирует цену хранения до расчёта стоимости: `effStorageSC = storageSC * 10 / CollateralScore`; `TotalCost'` считается по ней. Economics это Cost Score от `TotalCost'` (без весов). Прежняя формула `0.4*Cost + 0.6*Collateral` заменена вариантом E; оценка залога идёт по множителю «залог / цена хранения».
- Якорь стоимости (p10 от `TotalCost'`) и `m_ref` (p95 множителя залога) берутся **только по пригодным хостам** (без флагов непригодности, offline включён). Каждый просканированный хост оценивается по этим якорям.
- `performHostChecks` сначала проверяет все хосты, строит пул пригодных, затем считает Economics и сохраняет проверки. Пустой пул даёт Economics 1 для всех и одну строку лога.
- Хост с неположительным скорректированным `TotalCost'` не входит в пул якоря (оценивается якорем остальных, Cost Score 10); если ни у одного хоста пула нет положительной стоимости, якоря нет и все Score равны 1, как при пустом пуле.

**Пауза кандидата (`e3f950a4`).** Кандидат, у которого формирование ADD или REPLACE провалилось по вине хоста (исход failed, не вина рентера, не отмена контекста, не отсутствие записи снимка), исключается из `CandidateHosts` плана на 24 часа, при повторных неудачах подряд удваивается до 7 суток. Сформированный контракт очищает запись. Хранится в оперативной памяти (`smartRuntime`), при перезапуске обнуляется; оценки, портфель, продления и чистый планировщик не менялись.

### Учёт расходов и показатели контрактов

**Показатели из существующих данных (`5ac3c4ee`).** Новый маршрут `GET /bus/contracts/financials`: финансовые показатели неархивных контрактов одним запросом (My Data, Remaining Allowance, Σ collateral, Used Collateral и т. д.).

**Capacity, storage, ingress (`8e3107a3`, миграция `00067`).**
- Колонки `contracts.capacity`, `contracts.storage_spending`, `contracts.ingress_spending` (`DEFAULT 0`), sqlite и mysql, схемы синхронизированы.
- `capacity` берётся из ревизии контракта (RHPv4) там, где обновляется `size`.
- В `AppendSector` расход на запись (`uploads = RenterCost()`, как раньше) дополнительно раскладывается на `storage` и `ingress` из `usage`. Поле `uploads` не менялось.
- При продлении новые поля обнуляются у нового контракта, архивная копия старого сохраняется, как у остальных `*_spending`.
- API: `storage` и `ingress` в `ContractSpending`, `capacity` в ответе контракта.

**Egress (`e540f6f3`, миграция `00068_contract_egress`).**
- Колонка `contracts.egress_spending` (`DEFAULT 0`), sqlite и mysql.
- Запись: после **успешного** `ReadSector` значение `usage.Egress` попадает в накопитель по хосту (`SpendingRecorder`); раз в 5 секунд (`BusFlushInterval`) bus добавляет накопленное к **активному контракту хоста** (`POST /contracts/egress`). Дополнительных запросов к хосту и к БД на каждое чтение нет, поведение скачивания, повторы, таймауты и цена не менялись. Хост без активного контракта: накопленное отбрасывается без ошибки.
- Суммы по цепочке продлений: в `GET /bus/contracts/financials` добавлены `totalStorage`, `totalIngress`, `totalEgress`, `totalSpent`.
- **Σ spent** = `contractPrice + uploads + deletions + sectorRoots + egress`, **без** `fundAccount` (иначе двойной счёт). `Total()` в `ContractSpending` не менялся и не используется.

**Рекордер (`8bcc96ac`).** `flush` накопителя больше не держит мьютекс на время вызова bus; тест на конкурентную запись падает на старом коде и проходит на новом, `-race` чисто.

### Исправления

**Merkle-proof после продления (`98c3aa42`, `16cadbb3`, `48f1dbc5`).**
- Дефект был в upstream (`chainsubscriber.go` и `stores/sql/{sqlite,mysql}/chain.go` совпадали с `origin/master`, исправлений в `coreutils` 0.24.1–0.25.3 нет). Строка `contract_elements` продлённого контракта хранила `leaf_index` и `merkle_proof` прежнего контракта; обновления по позиции листа исправить их не могли. Из-за этого рассылка ревизий отвергалась (`file contract revision parent has invalid Merkle proof`, у контракта `a7d7896a` 3953 раза), а самостоятельное разрешение контракта (expiration) могло быть невозможным. Продление контракта дефектом не затрагивалось (хост присылает свой родительский элемент).
- `98c3aa42`: `UpdateFileContractElements` при конфликте обновляет `leaf_index` и `merkle_proof` вместе с `contract`.
- `16cadbb3`: `ExpiredFileContractElements` не возвращает уже разрешённые контракты (раньше для каждого renterd 144 блока подряд строил бесполезные expiration, 217 транзакций с 03.10).
- `48f1dbc5`: ошибки `chainsubscriber` пишутся через `Errorw` со структурными полями (раньше `%!(EXTRA zapcore.Field=…)`).

**Разовая починка испорченных элементов (`08922674`, `internal/bus/chainrepair.go`).**
- Один раз за старт, после первой успешной синхронизации, на горутине синхронизации: элементы всех активных контрактов проверяются по аккумулятору цепочки. Здоровая БД: ничего не пишется, одна строка лога.
- Для испорченных: replay `UpdatesSince` с точки за 144 блока до самого раннего испорченного контракта, только по ним, тем же путём, каким блоки применяются к БД. Пишутся только `contract`, `leaf_index` и `merkle_proof` в `contract_elements` и только после проверки по аккумулятору.
- Защиты: запись отменяется, если индекс БД изменился; строка с изменившимся `leaf_index` пропускается; диапазон не больше 20000 блоков; ошибка или паника только логируются, renterd работает дальше, повтор при следующем старте. Остальные таблицы и tip не трогаются. Новых настроек нет.
- На рабочей системе: `contract elements checked {"checked": 41, "invalid": 8}`, затем `contract elements repaired {"invalid": 8, "repaired": 8}` (replay около 64 с, 1779 блоков), на втором старте `invalid: 0`, рассылка ревизии `a7d7896a` прошла (`successful: 1`).

**Индекс `price_history` (`3738c027`, миграция `00069_price_history_index`).**
- Индекс `idx_price_history_host_type_created_at` на `(host_id, price_type, created_at)`, sqlite и mysql; прежний индекс по `host_id` оставлен, запрос не менялся.
- Якорный запрос `PriceHistoryPoints` на копии БД: 10,7 с → 0,31 с, результаты построчно совпали (на рабочей системе около 5 с → доли секунды). Создание индекса: 1,1 с, размер около 47 МБ.

## Как обновиться

Из ZIP (Windows amd64) содержимое: `renterd.exe` и `LICENSE`. SQLite, как на рабочей машине:

1. Остановить renterd. Бэкап БД на другой диск: `sqlite3 <db.sqlite> ".backup '<папка>\db.sqlite'"` и то же для `metrics.sqlite`; `PRAGMA integrity_check;` на копии. Сохранить копию прежнего `renterd.exe`.
2. Заменить `renterd.exe`, запустить. При первом старте выполнятся миграции `00067`, `00068`, `00069` (индекс создаётся за секунды), затем в логе `contract elements checked`, при необходимости `repairing contract elements` и `contract elements repaired`. Обновить страницу в браузере (Ctrl+F5).

**Откат:** вернуть прежний `renterd.exe`. По коду (`internal/sql/migrations.go`, `PerformMigrations`) старый бинарник только применяет недостающие миграции и не проверяет неизвестные записи в таблице `migrations`, поэтому стартует на БД с `00069`; для `00067` и `00068` это подтверждено на практике. Строки `contract_elements`, уже исправленные починкой, для старого бинарника безвредны. Если откат всё же не заработает, восстановить БД из бэкапа.

## Известные особенности

- **Σ egress это нижняя граница.** Хост списывает оплату за чтение до отправки данных, поэтому отменённые и неудачные чтения (overdrive, ошибки) оплачены, но renterd их не видит. Чтения по хостам без активного контракта не попадают никуда. Размер занижения по коду не оценить, нужна сверка (план ниже).
- **Данные накапливаются только с момента внедрения:** storage и ingress с первого старта с `00067`, egress с `00068`; у старых контрактов до этого нули, Σ spent поэтому неоднороден по периоду.
- **Σ collateral по строке контракта**, не по цепочке: у продлённого контракта залог текущего контракта.
- **Откат на старый exe после продления:** если на старом бинарнике произойдёт продление, egress нового контракта продублируется в архивной копии (то же верно для storage и ingress).
- **Номера миграций `00067`, `00068`, `00069` наши**, при слиянии с upstream возможен конфликт. MySQL-варианты миграций, починки и индекса не запускались (проверен sqlite).
- **SQL по датам** (`ce.created_at < c.created_at`) после починки по-прежнему показывает прежние строки, `created_at` не меняется; признак успеха: `contract elements checked` с `invalid: 0`.
- **Оконный запрос истории цен** (`created_at >= since`, окно 14 суток, около 195 тыс. строк) остаётся около 1,4–1,6 с: время уходит на выдачу строк. Вызывается раз за проход автопилота. Очистки `price_history` нет, рост около 13,7 тыс. строк в сутки.
- **Смешанные смещения `+02:00` и `+03:00` в `created_at`** влияют на якорь не больше чем на час на стыке перехода времени; не исправлялось.
- **Пауза кандидата** хранится в оперативной памяти и обнуляется при перезапуске.
- **Smart Resources: `ownData`** считается из `StoredData` (сумма `contracts.size` неархивных контрактов), поэтому завышен на размер prunable-данных. Не исправлено (влияние сейчас малое).
- В таблице Hosts ширины колонок не менялись.
