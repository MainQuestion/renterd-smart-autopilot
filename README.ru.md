# renterd Smart Autopilot

[English](README.md) | [Українська](README.uk.md) | Русский

>
> Этот проект является экспериментальной модификацией
> [SiaFoundation/renterd](https://github.com/SiaFoundation/renterd).
>
> Это не официальный релиз Sia Foundation, и в текущем состоянии его следует
> считать alpha-версией.

## Обзор

**renterd Smart Autopilot** — экспериментальное расширение Sia renterd,
направленное на улучшение оценки хостов, управления контрактами и, в
перспективе, принятия решений о размещении данных.

Долгосрочная цель — уйти от зависимости от одного непрозрачного рейтинга
хоста и перейти к прозрачному многомерному профилю.

Целевая модель:

```text
Host =
    Reliability
  + Performance
  + Resources
  + Economics
  + Risk
  + Technical Compatibility
  + Network Diversity
```

Эти измерения намеренно остаются раздельными.

Например, хост может быть очень надёжным и дешёвым, но медленнее остальных
хостов пула. Другой хост может быть быстрым, но создавать повышенный риск
концентрации инфраструктуры.

Smart Autopilot должен сохранять эти различия, а не скрывать их внутри одного
агрегированного числа.

# Реализованные возможности

## Настраиваемая оценка хостов renterd

Несколько параметров существующего механизма оценки хостов renterd, которые
ранее фактически были жёстко заданы, теперь можно настраивать.

Текущие параметры:

- вес свободного места;
- экспонента штрафа за нехватку места;
- коэффициент резерва при allocation;
- экспонента штрафа за взаимодействия;
- начальный уровень доверия к взаимодействиям;
- возможность отключать отдельные legacy-факторы оценки.

Значения по умолчанию предназначены для сохранения исходного поведения renterd.

Эти настройки доступны на отдельной странице **Scoring** в веб-интерфейсе
renterd.

Существующая оценка renterd не удаляется. Smart Autopilot развивается рядом с
ней, чтобы текущее поведение оставалось понятным и настраиваемым, пока новая
профильная модель развивается.

## Performance

Отдельный **Performance Score** оценивает реальную производительность хоста.

Он намеренно существует отдельно от исходной агрегированной оценки renterd.

Текущая реализация использует исторические измерения upload и download и
сравнивает каждый хост с текущим пулом.

Модель включает:

- историческую скорость upload;
- историческую скорость download;
- раздельную оценку upload и download;
- нормализацию относительно пула;
- P95 как референс производительности пула;
- логарифмическое сжатие шкалы;
- количество доступных измерений;
- комбинированный Performance Score.

История производительности оценивается в скользящем временном окне, а не только
по последней передаче.

В таблице Hosts отображаются:

```text
Performance
Upload
Download
```

`Performance` — нормализованный рейтинг.

`Upload` и `Download` показывают реально измеренную пропускную способность в
Mbps, чтобы рейтинг можно было сопоставить с исходными данными.

Performance остаётся независимым измерением и не умножается на legacy-оценку
хоста renterd.

## Economics

Отдельный **Economics Score** оценивает ожидаемую стоимость использования
каждого хоста для реального профиля хранения и трафика пользователя.

В расчёте учитываются:

- цена хранения;
- цена upload / ingress;
- цена download / egress;
- ожидаемый объём хранения;
- ожидаемый месячный upload;
- ожидаемый месячный download.

Профиль использования берётся из уже существующей конфигурации контрактов
renterd:

```text
Contracts.Storage
Contracts.Upload
Contracts.Download
Contracts.Period
```

Таким образом сохраняется единый источник данных для ожидаемого объёма
хранения и трафика вместо дублирования отдельных Economics-настроек.

Значения upload и download, хранящиеся за весь период контракта, перед
использованием в модели Economics пересчитываются в месячный эквивалент.

Для каждого хоста сначала рассчитывается ожидаемая суммарная стоимость:

```text
TotalCost =
    StoragePrice × StorageVolume
  + IngressPrice × MonthlyUpload
  + EgressPrice × MonthlyDownload
```

Затем результат нормализуется относительно текущего пула хостов.

Для дешёвого края пула используется percentile-reference вместо одного raw
minimum, чтобы один аномально дешёвый хост не искажал всю шкалу.

Результирующая оценка примерно означает:

```text
1 = дорого относительно пула
10 = среди самых дешёвых хостов пула
```

В таблице Hosts также показываются исходные:

```text
Storage price
Ingress price
Egress price
```

Это делает Economics Score прозрачным и проверяемым.

## Resources

Отдельный **Resources Score** оценивает текущую экспозицию рентера относительно
конкретного хоста и возможные последствия его потери.

Эта группа не ограничивается только количеством свободного дискового места.

Текущая модель использует семь сигналов.

### Данные и ёмкость

```text
Данные рентера на хосте
Свободное место
Место, занятое другими данными
```

### Финансовая и контрактная экспозиция

```text
Финансовая экспозиция на оставшийся срок контракта
Оценочная стоимость восстановления / миграции данных
Оставшийся срок контракта
```

### История потерь секторов

```text
Доля потерянных секторов
```

Семь параметров нормализуются относительно текущего пула.

После этого они объединяются в три смысловых блока, а не через плоское
равномерное усреднение 1/7:

```text
Block A = data / capacity
Block B = money / time
Block C = sector-loss share

Resources Score =
    (Block A + Block B + Block C) / 3
```

Такая структура намеренно даёт истории потерь секторов достаточный вес, чтобы
существенная доля потерь не растворялась среди остальных хороших показателей.

Resources отвечает на вопрос:

> Насколько дорогой и проблемной будет потеря именно этого хоста прямо сейчас?

Эта оценка существует рядом с legacy-фактором свободного места renterd и не
заменяет его.

В таблице Hosts могут отображаться исходные значения:

```text
Own data
Free space
Foreign data
Exposure
Recovery compensation estimate
Contract time remaining
Lost-sector share
```

## Risk Coverage

Отдельный **Risk Coverage Score** оценивает исторические изменения цен и
collateral хоста.

Текущая реализация отслеживает события, связанные с:

```text
Storage price
Ingress price
Egress price
Collateral
```

Количество зарегистрированных событий оценивается в настраиваемом историческом
окне.

Размер окна задаётся на странице **Scoring** через параметр Risk Price Window.

Текущее значение по умолчанию:

```text
14 days
```

В таблице Hosts отображается как сам Risk Coverage Score, так и исходные
счётчики событий, чтобы причина оценки оставалась видимой.

Эта группа намеренно отделена от Economics.

Economics отвечает на вопрос:

> Насколько дорог хост сейчас?

Risk Coverage должен отвечать на вопрос:

> Насколько стабильным было экономическое поведение хоста во времени?

---

## История хостов

Smart Autopilot сохраняет исторические наблюдения о хостах, которые могут
использоваться новыми механизмами оценки.

Текущие таблицы истории:

```text
speed_history
price_history
scan_history
```

Это создаёт основу для принятия решений на основе поведения хоста во времени,
а не только последнего scan или последнего snapshot настроек.

---

## Paused contracts

Smart Autopilot добавляет состояние контракта **Paused** между здоровым
контрактом и контрактом, который нужно сразу считать плохим.

Цель — не превращать каждую временную проблему хоста в немедленный жёсткий
failure.

Модель состояний контракта позволяет различать:

```text
Good
Paused
Bad
```

Временно проблемный контракт может оставаться в состоянии Paused, пока система
ожидает восстановления.

Если настроенный timeout или условия отказа превышены, контракт может перейти в
`Bad`.

Интерфейс Active Contracts показывает это состояние отдельно от исходной
good/bad логики.

---

## Группы в таблице Hosts

Таблица Hosts расширена отдельными группами Smart Autopilot.

Сейчас реализованы:

```text
Performance
Economics
Resources
Risk Coverage
```

Основной score каждой группы остаётся видимым, а исходные метрики можно
развернуть при необходимости.

Это важная часть дизайна Smart Autopilot: пользователь должен иметь возможность
понять, *почему* хост получил конкретную оценку.

## Настройки отображения таблиц

В **App preferences** доступны дополнительные настройки отображения таблиц.

Текущие параметры:

```text
Row size
Number size
Number weight
Number font
```

Для чисел можно использовать обычный sans-serif или моноширинный шрифт.

По умолчанию Smart Autopilot использует достаточно плотное представление,
чтобы большие таблицы хостов и контрактов было удобнее анализировать.

Сейчас эти настройки применяются к таблицам renterd:

```text
Hosts
Active Contracts
```

Инфраструктура настроек является общей для веб-приложений, хотя на текущем
этапе поведение применяется именно к указанным таблицам renterd.

# Архитектура Smart Autopilot

Целевая архитектура оценивает хосты по семи независимым измерениям вместо
полной зависимости от одной агрегированной оценки.

В текущей alpha-линейке уже реализованы четыре группы:

```text
Performance
Resources
Economics
Risk Coverage
```

Оставшиеся основные группы пока находятся в разработке:

```text
Reliability
Technical Compatibility
Network Diversity
```

Точные границы этих групп могут изменяться по мере дальнейшего изучения
реальных code paths renterd и доступных данных.

---

## 1. Reliability

Предназначена для описания того, насколько стабильно хост остаётся доступным и
выполняет свои обязательства.

Возможные сигналы:

```text
Uptime
Interaction history
Consecutive failures
Host age / historical presence
Scan history
```

Цель — отделить долгосрочную операционную надёжность от сырой
производительности.

---

## 2. Performance

Реализовано.

Оценивает, насколько быстро хост реально обслуживает renter workload.

Текущие входные данные:

```text
Upload speed
Download speed
```

с нормализацией относительно пула и отдельным видимым Performance Score.

В будущем группа может быть дополнена latency и operation-time метриками, если
renterd предоставляет их в достаточно надёжной форме.

---

## 3. Resources

Реализовано.

Оценивает текущую экспозицию рентера, ёмкость, стоимость миграции, оставшийся
срок контракта и историю потерь секторов.

Это намеренно шире, чем просто advertised free space.

---

## 4. Economics

Реализовано.

Оценивает ожидаемую стоимость хоста на основе реально настроенного профиля
storage, upload и download пользователя и сравнивает её с текущим пулом.

---

## 5. Risk

Частично реализовано через текущий **Risk Coverage**.

Существующий механизм оценивает исторические изменения цен и collateral.

В дальнейшем эта группа может получить дополнительные risk-механизмы после их
проектирования и проверки на реальных данных и поведении контрактов renterd.

---

## 6. Technical Compatibility

Планируется.

Эта группа должна определять, подходит ли хост технически для renter ещё до
начала ранжирования.

Возможные условия:

```text
Contract acceptance
Host announcement state
Successful scan completion
Required protocol support
Required host functionality
Other renterd usability gates
```

Часть этих проверок уже существует внутри renterd.

Smart Autopilot сначала должен определить и сохранить их текущее назначение и
семантику, прежде чем решать, как именно они должны участвовать в новом
профиле.

---

## 7. Network Diversity

Планируется.

Эта группа должна оценивать общий инфраструктурный риск между хостами, а не
рассматривать каждый хост полностью изолированно.

Возможные сигналы:

```text
IP address
Subnet
ASN
Geographic information, where reliably available
Infrastructure overlap with already selected hosts
```

Цель — уменьшить риск коррелированных отказов при распределении избыточных
данных.

---

# Принципы проектирования

## Сначала исследовать текущее поведение renterd

Изменения должны основываться на фактической реализации renterd, а не на
предположениях о том, как система, вероятно, работает.

Существующий механизм сначала исследуется и только затем изменяется.

---

## Сохранять существующее поведение там, где это возможно

Smart Autopilot развивается постепенно.

Цель — не заменить незаметно существующую логику renterd без понимания её
назначения.

Поэтому новые измерения профиля сначала вводятся рядом с уже существующими
механизмами.

---

## Делать оценку прозрачной

Один score может скрывать важные различия.

Например:

```text
Host A
Reliability:  9/10
Performance:  4/10
Economics:    8/10
Risk:         9/10
Resources:   10/10
```

Это часто полезнее, чем сводить все характеристики в одно число.

Там, где это возможно, показываются исходные измерения, чтобы нормализованные
scores можно было сопоставить с реальными данными.

---

## Сохранять пользовательскую настраиваемость

renterd уже предоставляет пользователю значительный контроль над поведением
renter.

Smart Autopilot должен расширять эту философию, а не заменять её новым набором
скрытых констант.

Параметры, существенно влияющие на политику или scoring, должны быть
настраиваемыми там, где это практически разумно.

---

## Разделять измерение и принятие решений

Оценить хост и решить, что с ним делать, — две разные задачи.

Текущая работа в первую очередь строит более богатый профиль хоста.

Будущий decision layer сможет использовать этот профиль для:

```text
Host selection
Contract formation
Contract renewal
Contract replacement
Data placement
Migration decisions
Network-diversity management
```

без необходимости сводить все измерения в один глобальный score.

# Статус разработки

Проект сейчас является экспериментальным alpha-программным обеспечением.

Реализация развивается постепенно параллельно с изучением фактических
механизмов renterd.

Текущий акцент:

```text
Host measurement
Transparent scoring
Historical observations
Contract state handling
User-visible diagnostics
Configurable behavior
```

Позже поверх этих измерений планируется создать интеллектуальный decision
layer.

В перспективе он может управлять:

```text
Host portfolio composition
Contract lifecycle decisions
Host replacement
Data migration
Data placement
Infrastructure diversity
```
